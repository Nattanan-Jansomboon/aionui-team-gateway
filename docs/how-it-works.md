# gateway ทำงานอย่างไร

เอกสารสำหรับคนที่อยากเข้าใจหรือแก้โค้ด และสำหรับตอนที่ AionUi อัปเดตแล้ว API เปลี่ยน

## ภาพรวม

```
┌──────────────┐  POST /ask   ┌────────────────┐  REST + WebSocket  ┌──────────────┐
│ web/index.html│────────────►│ src/gateway.py │───────────────────►│ AionUi WebUI │──► Team
└──────────────┘              └───────┬────────┘                    └──────────────┘
┌──────────────┐  MCP (stdio/http)    │ ใช้ make_client / aion_ask_team ร่วมกัน
│ MCP client   │────────────►┌────────┴────────┐
└──────────────┘             │ src/mcp_server.py│
                             └─────────────────┘
        ทั้งสองอ่าน/เขียน session ผ่าน src/session_store.py ──► session_state.json
```

| ไฟล์ | หน้าที่ |
|---|---|
| `src/gateway.py` | FastAPI: `/ask`, `/health`, `/session/status` และตัวคุยกับ AionUi (ส่งข้อความ รอผล อ่านคำตอบ ต่ออายุ session) |
| `src/mcp_server.py` | เปิด `aion_ask_team` เป็น MCP tool ชื่อ `ask_team` |
| `src/session_store.py` | เก็บ cookie / CSRF / refresh token ลงไฟล์ โหลดใหม่เมื่อไฟล์เปลี่ยน มี lock ข้ามโปรเซส |

## ขั้นตอนของ `/ask` (`aion_ask_team`)

ทุกขั้นยืนยันจาก DevTools และ `scripts/ws_probe.py` แล้ว

1. **อ่านประวัติแชตของ lead** `GET /api/conversations/{leadId}/messages?limit=200&content_mode=compact` เพื่อจดจุดเริ่มต้น (baseline) ไว้ตัดของเก่า
2. **เปิด WebSocket ก่อนส่ง** `ws://<host>/ws` ยืนยันตัวตนด้วย Cookie ตอน handshake ไม่ต้องส่งเฟรมสมัครรับข้อมูล
3. **ส่งข้อความ** `POST /api/teams/{teamId}/messages` ด้วย body `{"content": "<ข้อความ>", "files": []}` ตอบกลับทันทีเป็นใบรับเรื่อง มี `run.team_run_id` ใช้ติดตามรอบงานนี้
4. **รอสัญญาณจบรอบจาก event** ไม่เดาจากความเงียบ
   - `team.runCompleted` ที่ `team_run_id` ตรงกับใบรับเรื่อง = รอบงานจบ
   - `team.agentStatusChanged` (`working` / `idle`) ต่อสมาชิกแต่ละคน
   - ถ้าเจอ event ของรอบนี้ที่สถานะเป็น `failed` / `error` / `cancelled` จะรายงานข้อผิดพลาดทันที
5. **รอให้ทุกคนว่างต่อเนื่อง `AION_IDLE_GRACE` วินาที** (ค่าตั้งต้น 5) ก่อนถือว่าจบจริง เพราะใน log จริง หลัง `runCompleted` lead ยังถูกปลุกให้ทำงานต่ออีกสองสามวินาที และมี `idle` ชั่วคราวระหว่าง turn
6. **อ่านคำตอบ** จากประวัติแชตของ lead อีกครั้ง (ลองซ้ำได้สูงสุด 10 ครั้ง เพราะข้อความล่าสุดอาจเขียนลงประวัติช้ากว่า event) แล้วเลือกคำตอบด้วย `AION_ANSWER_MODE`

### การเลือกคำตอบ (`AION_ANSWER_MODE`)

หลังทีมทำงานเสร็จ สมาชิกส่ง idle notification มาหา lead แล้ว lead มักพิมพ์ข้อความสั้น ๆ ตอบ ("ไม่มีอะไรต้องทำ") **ตามหลัง** คำตอบจริง ถ้าเอาข้อความสุดท้ายเสมอ จะได้ข้อความขยะ

| โหมด | วิธีเลือก |
|---|---|
| `smart` (ค่าตั้งต้น) | ทิ้ง "ข้อความตอบโต้" คือข้อความของ lead ที่พิมพ์ทันทีหลังได้รับข้อความจากสมาชิกโดยไม่เรียกเครื่องมือคั่น (ยกเว้นยาวกว่าข้อความปกติที่ยาวที่สุด) แล้วเลือกข้อความสุดท้ายที่เหลือ |
| `longest` | ข้อความที่ยาวที่สุด |
| `last` | ข้อความสุดท้าย (พฤติกรรมเดิม) |
| `all` | ต่อทุกข้อความของ lead เข้าด้วยกัน ครบที่สุดแต่มีข้อความเล่าขั้นตอนปน |

`smart` เป็นการอนุมานจากลำดับเหตุการณ์ในประวัติแชตที่เห็น ถ้า lead ตอบสั้นกว่าข้อความเล่าขั้นตอนของตัวเองและพิมพ์หลังสมาชิกรายงานโดยไม่เรียกเครื่องมือ อาจเลือกพลาดได้ ถ้าเจอให้ลอง `AION_ANSWER_MODE=all` เพื่อดูทุกข้อความ

### ข้อจำกัดที่ควรรู้

- ขั้นที่ 5 ยังมีช่วงรอแบบกำหนดเวลา เพราะ AionUi ไม่มี event ที่บอกว่า "lead สรุปเสร็จสมบูรณ์แล้ว" โดยเฉพาะ ค่านี้ปรับได้
- ถ้าส่งข้อความตอนที่ทีมกำลังทำงานรอบอื่นอยู่ AionUi อาจรวมเข้ารอบเดิม (ใช้ `team_run_id` เดิม) gateway จะรอจนรอบนั้นจบ
- เทสต์ใน `tests/` ใช้ข้อมูลจำลอง ไม่ได้ครอบคลุมทุกลำดับ event ของ AionUi จริง

## Endpoint ของ gateway

| Endpoint | ทำอะไร |
|---|---|
| `POST /ask` body `{"question": "..."}` | ส่งคำถามให้ Team แล้วคืน `{"answer": "..."}` (จำกัด 10 ครั้ง/นาที/IP) |
| `GET /health` | `{"ok": true}` |
| `GET /session/status` | ตรวจว่า session ใช้ได้ไหม พร้อมวันหมดอายุ (ไม่เปิดเผยค่า cookie) |

รหัสตอบกลับของ `/ask` ดูใน [troubleshooting.md](troubleshooting.md)

## เมื่อ AionUi อัปเดตแล้วพัง

อาการทั่วไป: รอจนหมดเวลา (504) ทั้งที่ทีมตอบแล้วในแอป หรือได้ 4xx จาก endpoint ที่เคยใช้ได้ ให้สำรวจใหม่ตามนี้

### 1) เปิด DevTools

เปิด WebUI ของ AionUi ในเบราว์เซอร์ที่ pair แล้ว กด F12 ไปแท็บ **Network** แล้วติ๊ก **Preserve log**

### 2) จดข้อมูล

- **ตอนส่งข้อความหา Team:** ดู request ที่เกิด: URL, method, payload (ชื่อ field ของข้อความ, id ต่าง ๆ)
- **คำตอบที่วิ่งกลับทาง WebSocket:** กรองด้วย **WS** คลิกการเชื่อมต่อ แล้วดูแท็บ **Messages** ส่งข้อความหา Team อีกครั้งแล้วสังเกตว่า event ไหนบอกว่าทีมตอบจบแล้ว และ WebSocket ต้องส่ง token/auth ตอนเชื่อมต่อหรือไม่

> เวลาเอาข้อมูลไปให้ใคร (รวมถึงให้ AI ช่วยเขียนโค้ด) ให้ลบ cookie และโทเค็นแล้วใส่ `xxx` แทนทุกครั้ง

### 3) ใช้ `ws_probe.py` ดู event ทั้งหมด

```bash
python scripts/ws_probe.py
```

ตั้งตัวแปรเหมือนตอนรัน gateway (อ่าน session จากไฟล์เอง) แล้วไปส่งงานให้ทีมในหน้า WebUI รอจนตอบเสร็จ กด Ctrl+C

- หน้าจอ: เวลา + ชื่อ event + ฟิลด์สำคัญ (ซ่อน `team.sessionStatusChanged` เพราะเกิดซ้ำบ่อย)
- `logs/ws_probe.log`: ทุกเฟรมเต็ม ๆ บรรทัดละหนึ่งเฟรม ค่าที่ชื่อมี token/cookie/password ถูกปิดเป็น `***` แต่ในนั้นมีเนื้อหาแชตของทีม **ห้ามขึ้น Git** (`.gitignore` กันไว้แล้ว) และตรวจก่อนส่งให้ใคร

event ที่ gateway พึ่งพาอยู่ตอนนี้คือ `team.runCompleted`, `team.agentStatusChanged` (และ event ขึ้นต้น `team.run*` ที่สถานะล้มเหลว) ถ้าชื่อเปลี่ยน ให้แก้ `wait_for_run_done` ใน `src/gateway.py`
